# The Operating Model — Why Each Piece Exists

This is the reference for *why* the bootstrap generates what it generates. Every component below earned its place by a real failure (its **origin incident**) — these are scars, not theory. If you're deciding whether a piece is worth keeping in a given project, read its incident: the piece exists because the absence of it shipped a bug.

The model runs one person (Amin) as an orchestrator/PM over a fleet of sub-agents. The orchestrator plans, decomposes work into bounded slices, delegates, adversarially verifies, integrates, and keeps docs live — bringing the human only product/scope/architecture decisions. Everything else is mechanized so it can't be forgotten.

---

## 1. Orchestrator / PM (the main session)
Plans → decomposes into bounded slices → delegates → adversarially verifies → integrates → keeps docs live. Holds the conclusion, not the file dumps. It brings the human only the decisions a non-developer with strong system-design/product judgment is good at (scope, UX, "which behavior is right", approvals, anything billed/irreversible) and does everything technical itself.

**Why:** a lone coder implementing a multi-slice build breadth-first by hand drifts, skips verification, and asks the human dev-implementation questions they shouldn't have to answer. The orchestrator model decomposes + delegates + *adversarially verifies* instead.

## 2. The fleet (specialized lenses, each catches what the others structurally can't)
- **premise-and-architecture-challenger** — the read-only pre-plan lens: should this exist, is something already built/miswired/vestigial, where does the authority belong, what is the earliest wrong decision, and is the plan a durable root fix or a workaround? It returns options/verdict to the orchestrator; it is deliberately not a second PM.
- **sprint-kickoff-auditor** — the plan-reconciliation opening bookend: proves every settled decision/dependency is inventoried and consistent before implementation planning begins.
- **implementer** (+ Codex CLI for backend/non-visual throughput) — builds ONE bounded slice end-to-end, no "phase 2 later", self-reviews its own diff, runs the real gates.
- **adversarial-reviewer** — the general-doneness lens. Default stance: NOT done until it fails to refute. Hunts stale wiring, missed call sites, layered-not-replaced paths, test theater, hardcoded leaves, authority drift.
- **domain auditor** (the crown-jewel lens — the one piece authored per project) — the invariants this product cannot get wrong. Dialer: `compliance-auditor` (STIR/SHAKEN, TCPA, DNC, recording disclosure, tier boundary). CoachAI: `ai-decision-boundary-auditor` + `source-to-screen-auditor` (AI owns meaning; source reaches screen). **Why:** the adversarial lens alone left domain drift uncaught for multiple sprints (dialer, 2026-06-19 — a whole-app blind spot a user catch surfaced).
- **security-auditor / cybersecurity-auditor** — appsec/tenancy: auth/session, CSRF, RBAC/object-scope, tenant isolation, secrets, telemetry/PII, rate limits, SSRF/redirects, AI-prompt surfaces, supply chain.
- **doctrine-drift-auditor** — the code-vs-*our-own-doctrine* lens. Its single question: does the code do what our own ADRs/decision-log/authority-tiers/registries SAY — or contradict it? **Origin incident:** a compliance gate hard-blocked a stale DNC scrub (no override) while the project's own ADR classified that as a tenant-owned, disable-able capability — and the drift *survived the compliance audit* because the compliance-auditor's checklist encoded the wrong side of the contradiction. Only a lens that checks code against our words, AND our words against each other, catches that class.
- **ui-verifier** — the RENDERED-surface lens (frontend products only): computed styles + geometry at the project's breakpoints, keyboard/focus-visible, reduced-motion, loading/empty/error states actually rendering, fidelity to the approved mock. **Origin incident:** 2026-06-28, an invisible-at-tablet toggle shipped green because `verify`/`tsc`/the jsdom suite all passed — none of them can see `opacity: 0` or layout at a real breakpoint. Static gates + jsdom see source strings and a fake DOM, never pixels.
- **performance-auditor** — the scale lens: N+1 queries, unbounded reads, missing indexes for real query shapes, payload/DTO bloat, re-render storms, bundle growth, worker leaks. Static-first, every finding names a mechanism + a scale multiplier. **Why:** a real-time product that ships for months without a perf lens hides its first scale bug in an unaudited hot path.
- **functionality-parity-auditor** — the DELIVERY-CHAIN lens: decided → backend → shared contract → frontend api layer → consuming surface → nav/role reachability, both directions (nothing decided goes silently undelivered; nothing built goes silently unreachable). Pairs with a `gate:endpoint-wiring`-style contract-registry parity scanner as its mechanical floor where the project has an enumerable registry; re-triages that gate's PENDING/allowlist rows every run. **Origin incident:** Auxara Dialer 2026-07-08 — 6 backend endpoints with zero frontend references had accumulated invisibly across three sprints ("backend built, never wired, nothing caught it"); the class lives BETWEEN slices, where no per-diff review looks.
- **user-journey-auditor** — the ICP's-SEAT lens: researches how the real users work (web + the project's benchmark/sentiment docs), maintains a persona × moment use-case inventory, then WALKS each job through the app as built (entry → data → action → outcome → recovery), day-zero first. Reports job-blocking gaps, workflow loopholes, and improvement candidates as DECISION INPUTS (benchmark-cited, authority-boundary-framed, scrapped-scope-aware — it informs, the human decides). **Origin incident:** 2026-06-19 — every gate green, and the user found prod unusable end-to-end because one day-zero step was never built; no lens had walked the app from the user's seat.
- **release-verifier** — the DEPLOYED-product lens, run AFTER every production-affecting merge: deploy status, readiness endpoint, one core-flow smoke on the live surface, a new-error sweep. **Origin incident:** 2026-06-19, the user personally discovered a broken prod — "nothing works" — that every green CI gate had sailed straight past. CI green ≠ the container booted, the migration applied, a user can log in. The merge loop is not closed until this verdict lands.
- **test-runner** — the heavy-gate lens: runs the full `verify` + DB-backed integration suite in a disposable context and returns a compact pass/fail verdict. **Origin incident:** a long-running implementer dies on the verbose DB-test log; the orchestrator must not ingest it either. The verbose output lives in the runner's throwaway context.

Every reviewer/auditor lens is **read-only on the tree** and forbidden ALL tree-mutating git (see §6, PR #152). Each routes out-of-lane findings to the owning lens rather than dropping or duplicating them.

## 3. Mechanical gates (wire the gate, not the rule — vigilance erodes, wired controls don't)
- **PostToolUse hook** (`.claude/settings.json` → a gate-router `.mjs`) — after any Edit/Write, routes the edited file to its matching gate(s) and feeds a failure back to the agent (exit 2) so it must fix the violation before proceeding. The gate bites at edit time, not just in CI.
- **`gates:all`** — the aggregate the hook and CI both run. Always includes `gate:rules-wiring` + `gate:test-intent`; adds the project's domain gates.
- **`verify`** — the full local mirror of CI (build → lint → format:check → typecheck → test → gates:all). **Origin incident:** running `gates:all` alone (omitting lint/format/typecheck) let a banned import + unformatted files reach a RED main CI (2026-06-11). `verify` surfaces the whole cascade locally, before the commit.
- **`gate:rules-wiring`** — the loader-integrity gate. **Origin incident:** rules kept in TWO hand-synced dirs (`.claude/rules/` + a manual `.codex/rules/` mirror) DRIFTED silently — 5 files diverged, one agent went weeks without a rule. The fix single-sourced the rules and wired a gate that fails the build if a rule reference dangles, a rule goes undiscoverable, or the retired mirror returns. This is why the model uses ONE rules source, never a mirror.
- **`gate:test-intent`** — every test file declares what product decision it proves, and the `Proves:` IDs resolve to real requirements. **Why:** a test that compiles, runs green, and proves nothing is theater — worse than no test, because it manufactures false confidence.

## 4. Living docs (verified-not-trusted; fixed stale-on-sight)
- **`DOCUMENTATION_INDEX.md`** — the routing layer for authority docs, each with a freshness signal (`Status:` live/stub/historical).
- **`BUG_BACKLOG.md`** — real bugs found-but-not-fixed-now, with symptom + suspected cause + validation needed. Re-triaged at every sprint-close sweep.
- **`ARCHITECTURE_BLAST_RADIUS.md`** (+ a frontend one for UI products) — the connected-surfaces map; updated in the same turn a change reveals a missing relation.
- **`JOURNEY_LESSONS.md`** — the narrative lessons doc; the reusable *why*, captured so the next agent inherits it.
- **`decision-log.md` + `adr/`** — the decision authority (settled + scrapped/do-not-resurrect). Higher artifacts win: ADR > decision-log row > always-on rule > doc prose.

## 4½. The context layer (the window is a budget; the docs system is its supply chain)
The rules/docs structure above is also **context engineering for every future session**. Startup context is `CLAUDE.md`/`AGENTS.md` + recursive `@` imports + any `.claude/rules` file lacking official `paths:`. Everything else is just-in-time: path-scoped rules, skills, and docs behind `DOCUMENTATION_INDEX.md` (index → doc → source). Splitting a kitchen-sink file into imports does not save tokens. The bootstrap wires `gate:agent-context`, targets ~4K project tokens with a 10K ceiling, and records the measured files/total in the journey entry so growth is a visible decision, not drift.

## 5. The loops (bounded, and closed)
- **The merge loop is not closed until deploy is verified** (release-verifier, §2). A green CI is a lead, not proof.
- **Loop-discipline** — every do→verify→refine loop declares a measurable exit + a hard iteration cap; it escalates at the cap rather than spinning. Branch creation, commit, and PR creation/update are autonomous. Push is conditional on live proof of no preview/production deploy, publish or billed build, production write, or external contact; a preview counts as a deploy. Merge is conditional on the canonical action-authority evidence and must have no deployment/production effect; production-affecting push/merge, publish, prod-write, delete, deploy, billed actions, and external contact remain human-gated.
- **Closed-loop learning (doctrine-loop)** — every agent report carries a **"Doctrine-loop findings"** section: for each caught/missed bug, the root-cause LEAD (*why introduced? why did no control catch it?*) + the smallest control fix (gate > rule > agent-file edit > test > doc > backlog row). The orchestrator ROUTES every item the same turn — an unrouted item is a dropped lesson. When the RCA lands on "the auditor that should own this had no checklist row for it," the fix EDITS that agent file: the class becomes a checklist row or an entry in that agent's **"Learned classes (live log)"** trailer. The fleet's knowledge compounds instead of resetting per session. **Why:** a caught bug that leaves the fleet byte-identical will need re-catching by luck next time.

## 6. The integration model (worktree isolation + PR-based merge)
- Every parallel implementer works in its OWN `git worktree` on its own branch; the orchestrator's main checkout stays put.
- `main` is a GitHub integration target nobody commits to locally — branch → push → PR-merge lands server-side, so `main` is never contended. A local `main` kept to run the app is read-only (`git pull --ff-only`).
- **Worktree-paths pre-check.** **Origin incident:** 2026-07-02, an implementer edited the main checkout's copies (holding another agent's uncommitted work) using main-checkout absolute paths — two same-named trees exist during worktree work, and nothing mechanical forces the edit to the right one. The rule: every worktree edit uses the worktree's absolute path, and BEFORE running checks the agent confirms `git -C <worktree> status --short` shows exactly the expected files dirty. An empty worktree diff after edits means the edits went to the wrong tree.
- **Commit before dispatching a tree-touching reviewer.** **Origin incident (PR #152):** a read-only reviewer with Bash `git checkout`-ed away an implementer's uncommitted working-tree change while testing a mutation — even its self-restore wasn't trustworthy. So: committed work is the safety net (findings land as fixup commits), and every reviewer/auditor standing brief explicitly forbids tree-mutating git (`git checkout <file>`, `git stash`, branch switch, `git reset`).

## 7. The between-merge watch (uptime monitor)
A lightweight liveness/readiness probe (a cron-scheduled `uptime-probe.mjs` hitting `/api/ready` + the frontend shell, alerting on a red). **Origin incident:** the "detached-domain outage" class — a deployed surface that silently goes unhealthy between merges, with nobody looking. release-verifier catches a bad *deploy*; the uptime monitor catches a *drift into unhealthy* while no one is deploying. The `templates/ci/uptime-probe.mjs.template` + `uptime-runbook.md.template` give the probe + how to schedule it.

## 8. The between-session watch (orchestration automations)
Every new project registers two local, read-only Codex automations at bootstrap: a weekday orchestration-drift pass and a weekly doctrine/backflow review. They inspect tracked artifacts and safe summaries, never credentials/customer data/raw telemetry, and only propose changes. **Why:** lifecycle hooks catch an invalid action while a session is active, but they cannot notice a week of stale worktrees, context-budget creep, unpromoted learned classes, or a control that silently stopped running while nobody opened the repo. Registration is idempotent by exact automation name and is verified from the stored automation after creation.

The universal layer also has one operator-level biweekly backflow monitor, documented in `UNIVERSAL_BACKFLOW_MONITOR.md`. It compares the Auxara Dialer and Nuvora CoachAI tracked orchestration structures against these templates and safe global instruction surfaces. It proposes promotions only; it never edits either project or the universal layer. This is deliberately not copied into every bootstrapped project because one cross-repo monitor is the authority for universal promotion.

## The two reference implementations (same model, expressed differently)
- **Auxara Dialer** — the fullest instance: 9 project agents, rules single-sourced under `.claude/rules/*.md` (Claude @-loads, Codex reads via `AGENTS.md`), gates in `scripts/check-*.mjs` wired into `gates:all` + `verify` + a PostToolUse hook, CI with verify/docker-build/integration/notify-failure jobs, full living-docs set.
- **Nuvora CoachAI** — the adaptation proof: the SAME model with rules as `.cursor/rules/*.mdc` (Cursor-native, predates the split), a different domain auditor (`ai-decision-boundary-auditor` + `source-to-screen-auditor` — AI-boundary crown jewels, not telephony), and no `notify-failure` job (no alert channel wired). Proves what's invariant (the model) vs what adapts (rules format, domain auditor, alert wiring).

Use them as calibration, never as content to copy. Two projects with the same model and different crown jewels produce different domain auditors, different gate sets, and different registry tables — all correctly.
