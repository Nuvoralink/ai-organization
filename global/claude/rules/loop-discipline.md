# Loop Discipline — Iterate to Convergence, Never to Infinity

Purpose: a loop (do → verify against a bar → refine → repeat until the bar is met) is the highest-leverage way to reach quality — a review→fix→re-verify loop, a find-until-dry bug hunt, a converge-on-a-spec/golden/visual-match refinement, a bounded self-repair. **Default to looping whenever iterating beats one-shot.** But an *unbounded* loop is a footgun: it burns budget, thrashes in place, oscillates between two states, chases a moving target, or exits by trusting an unverified "done." This rule makes loops a standard tool **and wires the guardrails so no loop ever runs away.** Always-on for every agent. It is the execution-loop sibling of the doctrine-loop rule (which loops *the rules/docs* better each session).

## When to loop
Whenever the work has a **measurable convergence criterion** and iterating beats a single pass: review → fix → re-verify until 0 blockers; find-until-dry for unknown-size discovery (keep finding until K consecutive rounds surface nothing new); converge-on-a-target (iterate until a named gate is green / it equals a golden / it matches the locked mock); bounded self-repair (generate → validate → repair only the failed field → re-validate).

## The loop contract — declare these UP FRONT (a loop without them is forbidden)
1. **Exit criterion — explicit + measurable.** 0 blockers / 0 *new* findings / a named gate green / equality to a golden. The loop EXITS the instant it's met. No measurable exit → don't loop.
2. **Max iterations — a hard integer cap.** Default **3–5**, scale with stakes. Reaching the cap *without* convergence → **STOP and escalate** with the residual — never silently iterate past it.
3. **Progress requirement.** Each iteration makes *measurable* progress on the metric. An iteration with zero progress ENDS the loop (stall → escalate). No re-running the same step hoping for a different result.
4. **Budget bound.** Bounded by the turn's token/time budget; when it nears exhaustion, converge or escalate — don't open another iteration.

## Anti-infinite-loop guardrails (non-negotiable)
- **Bounded, always** — both a hard cap AND a measurable exit.
- **Monotonic progress or stop.** Improving → continue. Flat → STOP (stall). Worse → STOP (back out the last change).
- **No oscillation.** Track what's been tried; if a change is reverted then re-applied, or a finding fixed then re-flagged (A→B→A) → STOP and escalate; don't ping-pong.
- **Dedup against everything seen.** In find/discover loops, dedup each round against *all* prior findings, not just the last; exit on **K consecutive dry rounds** (K≈2), not a fixed total.
- **Don't chase a moving target.** If the exit criterion itself keeps shifting (spec, base branch, dependency) → STOP, re-baseline **once**, then resume.
- **The tier travels with EVERY load-bearing claim — this is GENERAL, not a wiring/absence special case (Amin directive 2026-07-30).** The two bullets below (verify-the-critic for a "clean", verify-the-finding for a "missing") are ONE discipline, and it governs EVERY claim class: *"X exists" · "the cause is Y" · "it passes / is done / works / verified" · "it's safe / tenant-isolated" · "X is missing / dead / broken" · "the fix is Z"*. Each piece of evidence proves exactly what it MEASURED and never the stronger thing it's tempting to conclude — a grep, a recalled fact, a read-inference, a subset-green, and above all **a sub-agent's summary** are all leads. Two hard obligations follow, and skipping either is the "something trusted too much" failure:
  1. **A sub-agent MUST verify its own claims against ground truth** — run the thing, open the persisted row / rendered surface / raw response, read the line — and label each load-bearing claim's tier (verified-by-running vs inferred/grepped). A claim it could only infer is flagged as such in its report, never delivered as fact.
  2. **What a sub-agent CANNOT verify from its seat, the ORCHESTRATOR verifies HANDS-ON before accepting or relaying it** — the DB-backed suite, the rendered UI at real breakpoints, the live/deployed behavior, the real provider response — exactly as a lone builder would, *the way we used to before delegating*. An agent's "it works / verified / clean" is the START of verification, never the end. The delegation model does not lower the verification bar; it only moves WHO runs the check, and when the agent structurally can't, that reverts to the orchestrator — it is never waived. (Live proof, 2026-07-30: an implementer reported M08 "committed and verified"; running its own DB lane — which it could not — surfaced its new test failing on a real DB constraint at fixture setup. Accepting "verified" would have merged a red test.)

  Default every relayed or agent-sourced claim to the WEAKEST tier and re-derive the load-bearing ones from the actual code/data/output. *Fail-state:* an agent's claim of any kind was accepted or relayed without the orchestrator re-deriving it from ground truth — and it was wrong, or true only at a weaker level than the voice that shipped it implied.
- **Verify the critic — the loop is only as good as the honesty of its feedback.** A reviewer/gate/sub-agent reporting "0 findings / clean / merge" is a **lead, not proof.** A critic fails two distinct ways and a trusted-but-unchecked "clean" hides both: (1) **confidently wrong** — it clears a real blocker on a false premise (e.g. reviewing the wrong diff/base); (2) **incomplete** — it reports clean having inspected only *part* of the surface (clears 2 of 7 issues, blind to the other 5). Catch both the same way: **re-derive the load-bearing claim from the actual code** — recount findings against the real diff; don't accept the summary. A *command's own exit status is part of this:* a command piped through `| tail`/`| tee`/`| grep` reports the **last stage's** exit code, not the command's — so `verify | tail` can print "exit 0" while `verify` failed. Read the real result: `set -o pipefail`, or capture `$?` *before* any pipe.

  **A sentinel must PROPAGATE, or it becomes the next lie (proven by experiment 2026-07-27).** The obvious antidote — `cmd; echo "EXIT: $?"` — is itself a masking bug: `echo` is now the sequence's LAST command and always succeeds, so the true code goes to the log while the **shell's exit status becomes 0**. Every consumer that reads a *status* rather than the log — a background-task notification, a hook, CI, an `&&` chain — then sees a false green. Measured: `bash -c 'false; echo "EXIT: $?"'` prints `EXIT: 1` and exits **0**. Required form, so the log-reader and the status-reader agree:

  ```bash
  cmd > /tmp/out.log 2>&1; rc=$?; echo "EXIT: $rc"; exit $rc
  ```

  A bare `cmd > log 2>&1` propagates naturally and is also fine. **Forbidden:** ending a command with a bare `echo`/`tail`/`grep` whose status replaces the one you care about. *Fail-state:* a real failure was announced as success because the last thing in the sequence was something that cannot fail.
- **Verify the FINDING at the level of the claim you ship — negative wiring evidence never becomes a product-absence claim (2026-07-30, three reversals in one day).** The mirror image of verify-the-critic: a critic's *positive finding* relayed to the human is a lead too, and it fails a third way — **level conflation**: the evidence is verified at one level while the shipped claim asserts a stronger one. A zero-grep / no-caller / no-reference result proves a WIRING fact about ONE pipe — it can never prove "the feature is missing / dead / has no button", because the capability may be served by a different pipe, an existing sibling control, or an auto-flow (CoachAI 2026-07-30: "alerts dead" — served by another working pipe and self-clearing; "agent-mapping screen missing" — it exists, the unwired pipe was a narrower duplicate; "no way to delete promo codes" — the deactivate toggle already covers it; each an unwired-PRODUCER row inverted into a product-absence conclusion, and the verify gate "passed" because the grep itself was true). Before any *missing / dead / broken / no way to X* claim reaches the human: walk the capability from the USER'S seat and ask the duplicate-vs-missing question — *is this unwired pipe the ONLY producer of this capability, or a parallel/superseded copy of one that works?* Then label every absence/breakage claim with its evidence tier: **PRODUCT-VERIFIED** (walked the surface; enumerated the candidate producers; all dead) / **WIRING-FACT** (this pipe has no caller; the capability may be served elsewhere — say so) / **RELAYED** (an agent's finding, not re-derived). **Default is RELAYED, and RELAYED/WIRING-FACT are presented as leads, never conclusions.** This is the findings-side twin of FIX-PROVEN/FIX-PLAUSIBLE — same disease (verified evidence + unverified conclusion in one authoritative voice), same cure (name the tier, default to the weaker one). *Fail-state:* a human inspected a report's "missing/dead" claim and found the capability alive via another pipe — and one wrong claim class poisoned trust in the entire report channel.
- **Escalate, don't spin.** Cap hit / stalled / oscillating / criterion unstable / a blocker you can't auto-resolve → hand back with the residual + what was tried. **Escalation is a successful termination, not a failure.**
- **Apply the action-authority matrix at the state-changing step.** Branch/commit/PR may proceed inside the authorized scope. A push may proceed only after live repository evidence proves that the ref update cannot trigger a preview/production deployment, publish, billed build, production write, or external contact; when branch pushes auto-deploy, the push inherits that action's human gate unless an exact no-deploy path is proven. A preview deployment still counts as a deployment. Merge is conditional: every listed proof must be re-derived from the actual diff, including no deployment/production effect; uncertainty requires a human. Production-affecting push/merge, publish, prod-write/config, data migration, delete, send/external contact, deploy, billed action, and unresolved product/design/material-architecture decisions remain human-gated. Killer mutation: call a Vercel/Netlify/Railway-integrated PR push "git-only" and push without inspecting current checks/integration configuration. Counterexample: a branch push to a repository with verified no push-triggered external effect remains autonomous. The action lives in a separate tool call after its sensor result has been read; never chain `check; act`.

## Work reaches a terminal, visible state — merged, ready-for-merge, or escalated (never orphaned)

A finished unit of work is NOT "done" until it reaches one of three **terminal, visible** states. A committed **local branch that is not pushed, not in a PR, and not surfaced is NOT a terminal state — it is orphaned work**, and orphaned work is a fail-state: built, verified, then lost because nothing carried it to use. (Anchor 2026-07-24: a fully-built, verified CI drift-gate sat on an unpushed local branch for two days — invisible, un-merged, nearly lost; found only when the founder asked. A ~40-branch sprawl was the same disease.)

**The three terminal states:**
1. **Merged** — for work within autonomous/conditional merge authority. In an **auto-deploy repo** (a branch/main push rebuilds prod), the line is **runtime effect, not "a build ran"**: a merge whose deploy is a **functional no-op** — docs, tests, tooling, gates, scripts, CI config, comments; **no change to the running app** — is auto-mergeable (verified, low-risk, additive, and not security/auth/billing/schema/data/provider/AI/visible-UI). The agent/orchestrator MERGES it after verification; **parking it is the fail-state.**
2. **Ready-for-merge** — for work whose deploy **changes runtime behavior** (frontend, backend, migration, config, visible UI, product). Human-gated. The moment it's done: **push + open a PR + flag it "READY — needs human merge"** and add it to the tracked queue. A finished-but-unpushed branch here is orphaned; push + PR + surface it immediately, never "later."
3. **Escalated** — for work that is **not mergeable** (blocked, incomplete, needs a decision): surface it with the **specific blocker** and what would unblock it.

**Merged ⇒ deleted.** The same step that merges a branch **deletes it — local branch, remote branch, AND the worktree** (clean-up-after-yourself). A squash-merge does not auto-delete the source, so the merger deletes it explicitly; a merged branch left alive is stale clutter that hides the real state.

**Enforcement:**
- **Every agent's done-report NAMES its terminal state** — `merged <sha>` / `PR #N — ready, needs human merge` / `escalated: <blocker>`. "Built + committed to a local branch" is not a terminal state.
- **The orchestrator never moves past a finished slice** without landing it in a terminal state, and **surfaces the merge queue at every checkpoint** — *built / merged / awaiting-merge / blocked* — so the human has the picture without chasing it.
- **At SessionStart/PostCompact the orchestrator RECONCILES every branch + worktree** against merged state: work already on main → delete the branch (+ worktree); unmerged finished work + no open PR → an **orphan**, resolve it (merge / push+PR+surface / escalate); a backup/checkpoint branch past its purpose → delete. Stale branches and orphaned work are swept, never accumulated.

*Fail-state:* a finished, verified unit of work sat on an unpushed local branch with no PR and no escalation — invisible and un-merged — or merged branches piled up undeleted because nothing deleted them at merge time.

## Cadence (the orchestrator picks per task)
- **Auto-converge (default):** run to the exit criterion *within the cap*, then surface the result + iteration log. Best when the criterion is crisp. "Auto" still means *bounded* auto.
- **Pause-per-iteration:** surface after each iteration for a human checkpoint. Use when the criterion is fuzzy, the blast radius is high, or each iteration is expensive/irreversible.

## Report
State: the exit criterion, iterations run (**n / cap**), the convergence metric per iteration, and how it terminated — **converged / escalated-at-cap / escalated-on-stall / escalated-on-oscillation**. A loop that "just finished" without naming its criterion + iteration count is a black box.

*Fail-state:* an agent ran a "keep going until it's good" loop with no measurable exit and no cap — and it spun on the same finding, oscillated, chased a moving criterion, merged without satisfying every conditional proof, or crossed a human-gated action on a critic's unverified "clean".
