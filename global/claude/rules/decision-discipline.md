# Decision Discipline — Research, Reason Structurally, Never Decide Silently

Purpose: stop mid-flight coin-flips. When implementation forces a choice the plan didn't settle, the quality of that unplanned decision is what separates durable work from drift. The compact router's decision core is always on; every agent (orchestrator, implementer, reviewer; Claude or Codex) must load this full authority for every unsettled mid-task choice, not just architecture.

## 1. When this rule fires
Any choice not already settled by an authority: library/dependency selection, schema or contract shape, API design, algorithm/pattern choice, naming a new domain concept, error/retry semantics, storage/queue topology, security-posture details, test strategy for a new surface, a UX micro-behavior the mock didn't specify — any tradeoff with more than one defensible side.

## 2. The decision ladder (in order — skip no rung)
1. **Authorities first.** Check the repo's settled truth before "deciding" anything: the decision log, ADRs, the product/architecture docs, the always-on rules, central registries/tokens, blast-radius maps, Project cards/issues, and the brief itself. Most "decisions" are already made — implementing against them is not a decision, and deviating from them is a STOP, not a choice. **Replace the decision; do not append a competing version.** When an explicit approved decision changes an existing premise, rewrite the owning decision row/card/doc in place and update every live projection in the same change: ADR summaries, PRD/sprint prose, source maps, Project cards/issues, backlog rows, tests, config, and implementation briefs. Delete the retired claim from living authority. Git history or a clearly isolated archive is provenance; current docs and Projects are projections of present truth, not append-only event logs. A precedence banner, “latest wins” footnote, bracketed amendment trail, duplicate decision ID, or new card that leaves the old claim live is not reconciliation. Create a new decision only for a genuinely independent premise; an immutable legal/audit event log may remain append-only, but it must derive one singular current projection. Verify the newer artifact is actually founder-approved rather than an implementation accident; ambiguity or any apparent legal/security weakening escalates. Finish with an old-claim sweep and reread every mutated external card. *Fail-state:* a reader must perform timestamp or supersession archaeology to discover the policy that applies now.
2. **Research before inventing — and research-first is the DEFAULT for anything NEW (Amin directive 2026-07-22).** If genuinely unsettled, research how mature products and industry best practice handle it (web search when available; otherwise state explicitly what the judgment rests on and name the uncertainty). Comparable-product prior art beats your first idea. **Stronger for new builds:** when the work CREATES something new — a surface, feature, architecture, workflow, pattern — the comparable-product/best-practice research pass is a required input BEFORE the first design/mock/dispatch, not a fallback for when options feel close. Scale it to stakes (full research pass for a new surface/architecture; quick comparable-check for a small addition; skip only pure mechanical fixes), and carry the artifact (products studied + patterns + recommendation) into the brief/mock. **Research output is filtered BACK through rung 1 before it enters any brief or decision:** tag each researched pattern authority-consistent or authority-conflicting (naming the governing decision/ADR); prior art a settled decision forbids is listed as FORBIDDEN with its authority, never as a neutral option (2026-07-22: a comparable-product ring-all pattern the project's own ADR forbade arrived in a dispatch brief looking settled). **Research has a SOURCE layer and a COVERAGE contract, and both are load-bearing (2026-08-06).** *Source:* which sites are reachable is a runtime property of our fetch path, not a guess — the first agent to hit a hard block WRITES IT DOWN in the project's research-source runbook (`docs/runbooks/competitive-review-research.md` where the project has one), so the next agent doesn't rediscover it by spending attempts; read it BEFORE the first fetch. (Verified 2026-08-06: TrustRadius, Gartner, G2, Trustpilot and Reddit hard-403 us; Capterra is the only source returning attributed review bodies, and only with explicit `?page=N` pagination plus a prompt that names reviewers or demands complete Cons text — a generic "extract quotes" returns just the aggregated summary block.) *Coverage:* **a WebFetch summariser's completeness claim is NEVER the researcher's coverage claim** — it reports on the payload it was handed, cannot see the pages it was not given, and will still volunteer totality language ("After reviewing all 919 reviews displayed on this page" for a page rendering ~25). Bound every NOT-FOUND to the pages actually retrieved ("not found in pages 1–5 of an unknown total"), never repeat a summariser's "all N" as your own coverage, and remember absence needs far more pages than presence — one page can prove a complaint exists; no number of pages proves one does not. This is the research instance of loop-discipline's verify-the-finding-at-the-level-of-the-claim-you-ship, and the bound travels with the claim into the brief, the decision row, and the human-facing report. *Fail-state:* something new was designed or built from the first idea with zero prior-art input — or a page-1 sample became a whole-corpus absence claim because a summariser's completeness language was relayed as the researcher's coverage.
3. **Reason structurally — visible, not vibes.** Work the choice through an explicit decision matrix (options × criteria: correctness, durability, security, tenant isolation, maintainability, doctrine fit, cost) or a written chain/tree-of-thought. Minimum bar: at least two real options, and the rejected option's strongest argument stated honestly — a one-row matrix is theater.
4. **Decide only with sufficient evidence — otherwise ESCALATE.** Escalate to the orchestrator (who researches/decides, or asks me) instead of deciding when: the options stay close after research; the blast radius is high; the choice is one-way/hard to reverse; security, billing, or a regulatory invariant is implicated; or the choice would contradict any settled authority. Hand over the matrix + your recommendation — an escalation with a good matrix costs minutes; a silent wrong guess costs a re-implementation. **A decision escalated to the human arrives with rung 2 ALREADY RUN** — options grounded in researched prior art, never first-idea forks the human must send back for research.

## 3. Nothing is decided silently
Every non-trivial mid-task decision appears in the report-back: what was decided, the options considered, the basis (authority / research / matrix), and what would invalidate it later. Architectural decisions additionally go to the decision log / an ADR. "I just picked one" is a bug even when the pick is right — an unrecorded decision can't be reviewed, can't be deliberately reversed, and silently becomes load-bearing. The orchestrator enforces this on agent reports: a diff containing an unreported decision is a finding.

*Fail-state:* an agent picked an approach mid-task without checking the authorities, ignored a later explicit decision because an older mock said “locked,” layered a new decision beside stale docs/Project cards instead of replacing their current projection, treated any newer file as automatically authoritative without verifying it was a decision, or shipped the choice without research/a visible matrix/reporting — the orchestrator discovered it only by reading the diff.
