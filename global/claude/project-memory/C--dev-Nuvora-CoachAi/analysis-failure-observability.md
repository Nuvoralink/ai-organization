**Analysis-run failure observability** (shipped 2026-07-08, PR #182):

- A failed analysis run used to only hit stderr (`safeLogEvent('error','analysis_run_failed')`) + set `Session.status='analysis_failed'` — it NEVER reached Sentry, so it couldn't be alerted on. Sentry only caught route 500s, process crashes, AI-provider fallbacks, retention errors.
- Now `runAnalysis.ts` calls `captureServerException(error, { route:'analysis.run', extra:{sessionId} })` in the failure path, gated by `shouldAlertAnalysisFailure()` (`backend/src/lib/analysisFailureAlerting.ts`) — a pure predicate that fires ONLY for genuine system/pipeline `analysis_failed`. It suppresses the 3 non-actionable classes: a user cancel, the benign completed-feedback race, and user-input `upload_failed` (bad/short/ineligible audio). So the page-me signal stays high.
- **The email alert:** a Sentry Issues alert rule filtered on tag `route` = `analysis.run` → email. Amin sets it in the Sentry UI (backend project → Alerts → Create → Issues → IF tag route=analysis.run → THEN email). No-ops in code when `SENTRY_DSN` unset.

**Incident + lesson (2026-07-08, hotfix PR #183):** PR #182's test broke the Railway backend build — it imported `vitest`, but **backend `src/**/*.test.ts` MUST use `node:assert` + tsx** (registered as a `test:regression:*` script), NOT vitest. Reasons: the prod build is `tsc -p tsconfig.json` which compiles ALL of `src/**` (test files included) with NO devDeps, so a vitest import → `TS2307 Cannot find module 'vitest'`; it passed locally + in CI because vitest was hoisted there (CI does NOT run a prod-parity/`--omit=dev` build — the gap that let it through). Also any `console.log` in a backend `src` file (the node:assert PASS-log convention) must be classified `script_only_allowed` in `docs/app-plan/srp-002-telemetry-sink-inventory.json` or the `DCD-SRP002-9` doc-code-drift gate fails. Durable-control follow-up (not yet done): exclude `**/*.test.ts` from the backend prod tsconfig, or add a prod-parity build to CI. Same hotfix also fixed a real **P2002 race** the concurrent roster test caught: use `err.code === 'P2002'` (NOT `instanceof Prisma.PrismaClientKnownRequestError` — fragile across the pg-adapter) and note **Prisma `upsert` is not atomic on Postgres** (two concurrent upserts of the same key can both INSERT → one violates the unique constraint; use create + P2002-swallow). See [[worktree-stale-shared-dist-falsered]].

**Event-driven auto-investigate webhook — DEFERRED 2026-07-08 (Amin decision):** the idea was Sentry alert → webhook → auto-start a Claude investigation. Held at ~0 live traffic; when a failure email lands, Amin pings me and I investigate in a session (deeper — full repo access). Revisit at launch. Two honest blockers when we do build it: (1) the claude.ai external-trigger API is **research-preview** — my real `RemoteTrigger` tool is `POST /v1/code/triggers/{id}/run` (OAuth in-process); a `claude-code-guide` research pass CONFABULATED a contradicting `/v1/claude_code/routines/{id}/fire` bearer endpoint, so DON'T trust it — verify the real contract against authoritative docs (likely auth-gated; ask Amin to fetch) before building. (2) Backend has NO GitHub integration today (no token/octokit), so "auto-open a GitHub issue" = a new outbound integration + credential; email (existing infra) is the zero-new-credential delivery. Reuse the HMAC-verify inbound-webhook pattern from `auxaraDialerWebhook.ts`/`dialpadWebhook.ts`. See [[gtm-readiness-threshold]] (0-user stage) and [[amin-perfectionism-ship]].
