Amin corrected this twice on the Tier-2 "Lead detail" drawer mockup (2026-06-10): I kept treating a dialer surface like a CRM lead profile.

**The two errors:**
1. **CRM intelligence on a dialer card** — "why they're a lead", interest/status taxonomy, attempts, prior-call notes, full attribute dumps. Leads come from *lists, not a CRM* (master plan line 9); the product has *"no CRM ambitions"* (line 86); CRM sync is *"sync only; we are not a CRM"* (line 170). Lead intelligence lives in the CRM and with the booker.
2. **A "cleared to call" badge** — the dialer claiming authority over a decision that isn't its. Whether to call this person, now, is the **human's** judgment. The compliance gate (calling hours, DNC) enforces the **legal floor silently at the moment of dial** — it blocks an illegal dial with a reason; it is **never** a pre-emptive per-lead UI verdict.

**Why:** This is the ARC-006 authority boundary applied to the *design/content* layer, not just to features/code. The rule exists in [[design-system-locked]]'s rule set, but I violated it in pixel/field choices anyway — so the tell is worth holding explicitly.

**How to apply:** Before putting any field on a dialer surface, ask *"is this dial context, or lead intelligence?"* Dialer-appropriate = identity (name, phone), basic list fields (city/state), number/call/config detail, disposition controls. CRM-owned = lead lifecycle, why-they're-a-lead, scoring, history-as-profile. And **never render a call-clearance/"safe to call" verdict** — the human decides; the gate enforces invisibly.

**Amin's locked lead surface for the dialer: name + phone + city/state + local time** *(⚠ SUPERSEDED 2026-06-21 — this was the original BASE; since lifted to "display any tenant-supplied field, tiered." Read the CURRENT TRUTH at top + the refinements below.)* — the basic fields from the imported list, plus the prospect's local time (cheap area-code/state→zone lookup) so the booker isn't dialing at a bad hour. Local time is allowed precisely because it's *informational* (informs the human's timing call) and *cheap to derive* — contrast the **script/opener, which he scrapped** (templating + merge-fields + per-campaign authoring = real backend scope the dialer doesn't need). The test for a borderline field: is it cheap dial-context that *informs* the human, or does it need backend authoring / make a decision for them? Default to *less*; everything richer stays in the CRM.

**REFINEMENT (Amin, 2026-06-21) — AUTHORITY ≠ SHOW-CAPABILITY. Don't over-apply this boundary (I did, in the Kixie gap analysis).** The boundary is about *who OWNS/DECIDES* — the CRM is the system-of-record; the human decides who/when to call — NOT a hard cap on which fields we may DISPLAY. We **can show additional fields the tenant uploaded in their list CSV**: have a **general import template** with optional fields, and **if the data for a field exists, show it** (tiered per the Tier-1/2/3 model so it never clutters the call). Showing tenant-provided data is **not** becoming a CRM. So "name+phone+city/state+local time" is the **base/default, not a ceiling**. What stays forbidden is unchanged: WE don't *source / own / score* lead intelligence, don't pull from the CRM as system-of-record, don't build a profile, and never render a "cleared to call" verdict. This **refines ARC-006 / doc-31 `UX-DONT-012` "CRM data creep" + the name+phone+city/state line** — the anti-pattern is CRM *creep / ownership / clutter / decision-making*, NOT displaying tenant-supplied CSV fields.
