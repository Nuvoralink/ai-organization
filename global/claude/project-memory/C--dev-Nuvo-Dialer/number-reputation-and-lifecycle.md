**Settled 2026-06-30 (user-approved; ADR-NUM-001 + ADR-NUM-004 revisions + decision-log NUM-001/NUM-004; PR #138).** Three connected number-surface decisions:

1. **LEAN LIFECYCLE — dropped `warming`; `cooling` → reversible `rested`.** States are now `active → inbound_only → released` + `rested`; new DIDs enter at **`active`** (no ramp). Warming was a weak-evidence reputation ritual (carrier analytics flag on call PATTERNS not a volume ramp; single-line per-number volume is inherently low; clean-buy NUM-008 covers recycled-number risk; "maturity" accrues with age+use, not a ramp). NUM-007 ported-entry carve-out now moot (bought + ported both enter `active`). Implementation: drop WARMING from `numberLifecycle.ts` + the worker's warming-promotion logic + `OUTBOUND_ELIGIBLE_VALUES` ([active,warming]→[active]); migrate `warming` rows→`active`; keep the `cooling` enum key but relabel display to "Rested" (avoid an enum migration).

2. **REPUTATION TWO-STATE.** State A (NO provider wired = the DEFAULT): show NOTHING reputational — no flags, no "Flagged — needs you" KPI, no health filter/tab/timeline; make NO decisions (no notifications, no auto-rest; rest is manual). A distinct **`not_monitored`** health state (≠ `calculating`). State B (provider wired): the detect→notify→opt-in-rest flow runs; `calculating` only while a real check is pending. Gate the whole reputation surface on a derived `reputationMonitoringEnabled`.

2b. **CAPABILITY DISPLAY = 10DLC status, US numbers ONLY** (user-clarified 2026-06-30 off the design re-check — went Voice-only → then this; don't re-litigate). **Drop the Voice AND SMS capability pills/column entirely** — every owned DID is both voice- and SMS-capable by default = always-on plumbing ([[no-plumbing-in-ui]]). The ONLY actionable capability signal is **10DLC registration, US numbers only** (`registered` / `pending — set up 10DLC →`). **Canada DIDs need NO 10DLC** (CASL mechanics, not 10DLC — ADR-CMP-001) → show **nothing**. Derived field = a US-only `tenDlcStatus` (`registered`/`pending`; `n/a`=CA=render nothing), NOT a generic `smsCapable`. Impl brief carries it.

3. **MONITORING PROVIDER = Telnyx Number Reputation API.** Self-serve on our EXISTING Telnyx stack (no contract), aggregates the carrier-analytics layer (Hiya/TNS/First-Orion). **Confirmed pricing (telnyx.com/pricing/numbers, 2026-06-30): $100/mo MRC flat (per account, not per number) + $0.10/reputation check + $1/remediation check; cached reads FREE.** ~$210/mo for ~50 DIDs monitored business-daily vs DNC.com's ~$58/number/mo (~$2900/mo) — it satisfies the prior "park until an affordable per-number signal exists" decision's OWN escape condition, so monitoring is un-parked but OPTIONAL (prevention-first stays primary: clean-buy NUM-008 + rotation + velocity caps OPS-007; Telnyx is the cheap overlay to MEASURE). Replaces the `fcr` shell adapter with a `telnyx` adapter.

**ANTI-PATTERN (do NOT re-litigate):** a generic "spam-check API" (SkipCalls / Call Control / IPQualityScore = a crowd-sourced REPORTED-spam DB) answers "is this a known spammer?" — it returns a dangerous **FALSE-CLEAN** on our own legitimate DIDs even when a carrier shows "Scam Likely". Only the carrier-analytics-layer read (Telnyx aggregates it) is valid for monitoring OUR reputation. (Reported-spam DBs have a possible future niche — screening a freshly-bought/ported DID against known-bad history — but that is NOT reputation monitoring.)
