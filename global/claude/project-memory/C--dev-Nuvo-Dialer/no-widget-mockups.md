Do NOT use the `mcp__visualize__show_widget` tool (or any generic widget renderer) to mock up dialer UI for Amin's approval. He said (2026-06-20): "the widget shows me nothing in relation to the actual app, it looks good in the widget but i have no idea if it will look good in the app too or not… moving forward dont use the widget."

**Why:** the widget renders in claude.ai's design system (flat, no depth/frost, different tokens, 680px) — it can't reflect the dialer's actual look (the locked depth/frost tokens, full width, real components), so it's useless for judging "will this look good in OUR app."

**How to apply:** for any visible dialer change, the mock = the **real thing in our design system**. Either (a) build it in the React app and deploy a **preview URL** for him to judge (nothing to prod until he approves), or (b) refine the real-design-system HTML mock (`frontend/public/explorations/*.html`, the locked surfaces) and show that rendered. This still honors mockup-first ([[design-system-locked]]) — the artifact just has to be faithful. Build-then-decide on a preview is acceptable to him when a faithful static mock is impractical.

**Mock only BACKABLE data (Amin, 2026-06-21).** "Don't put something we have no plans of creating the backend for… it's fine if it's a placeholder as long as we will have the capability to generate it." Before putting any metric/field/value on a mock surface, verify it's **deterministically buildable from data we already capture (or have a clear planned slice for)** — and know which kind it is: deterministic telephony/DB math vs needs-AI/transcript. Example that passed: the cockpit session ticker (Queued/Dialed/Answered/Connected/**Talk Time**) — all 5 are deterministic from `call_events` + dispositions + queue (Talk Time = summed `answered`→`hangup` durations; NO AI/transcript — that'd only be needed for talk-to-LISTEN ratio, which is CoachAI's job). A placeholder is fine; a placeholder for a capability we won't build is not — flag it, don't show it. (Sibling of the global "honesty without usefulness" / "build it to work" doctrine + the no-internal-narrative rule.)

**Mock iteration = LOCALHOST, not push (Amin, 2026-06-21).** GitHub Actions minutes are depleted, and every push to a branch triggers CI (verify/docker/integration) → burns minutes. The repo runs on **Amin's own machine**, so iterate mocks on the LOCAL dev server: `preview_start` the `frontend` launch config (port **5180**) → give Amin **`http://localhost:5180/explorations/<file>.html`** → he refreshes to see edits. NO git push, NO Vercel preview/share-link for mock iteration (the Vercel-preview + `get_access_to_vercel_url` dance was the OLD way, only needed when he's remote — on the same machine, localhost is direct + free + instant). Only push REAL code (which needs CI); if a push is ever blocked (Actions disabled), tell him. Merge gate stays local `npm run verify` regardless ([[ci-not-gated-on-main]]).

**Extends to REAL-CODE branch/PR review, not just mocks (Amin, 2026-06-29).** I pointed Amin at a **Vercel PR preview** to review the onboarding feature branch; he replied: "dont put mockups on vercel i cant login to check them, spin up the local servers." So for ANY review (mock OR a built feature on a branch), the path is **local servers on that branch**: `git checkout <branch>` in the MAIN checkout (it has `backend/.env`; retire the agent worktree first if the branch is held there — a branch can't be checked out twice) → start backend + frontend → give him **`http://localhost:5180`**. Vercel is effectively NEVER Amin's review path.

⚠ **Backend dev gotchas (2026-06-29, hard-won):** (1) `tsx watch` (the `dev:backend` script + the `preview_start` "backend" launch config) **HANGS on this Windows machine** — the chokidar file-watcher over the big tree never settles, so it never binds 8080 and prints nothing (looks identical to a crash). Run **no-watch** instead: `cd backend && npx tsx src/index.ts` (background). (2) It **cold-starts ~26s** (slow tsx compile, loaded machine) — wait 30s+ before concluding it's broken. Verify with **`curl localhost:8080/api/auth/me`** (→ `{"user":null}` 200) — **NOT `/api/ready`**, which HANGS when Redis is down (it probes the queue → never resolves → looks like a false "still down" / HTTP 000). netstat `:8080 LISTENING` + the log's `server_started` line also confirm it's up despite the Redis-error flood. (3) `REDIS_URL=localhost:6379` is **down locally but non-blocking** — just `ECONNREFUSED redis` warnings, NOT the hang (the tests prove startup tolerates it). (4) `DATABASE_URL` is **Neon (cloud, reachable)** — so the dev backend hits the **PROD Neon DB**; signups/test tenants land in prod (the source of the `*@example.test` prod accounts). Frontend = Vite on **5180** (launch.json `--port 5180 --strictPort`, proxies `/api`→8080); backend `PORT=8080`. (5) **Local browser AUTH is blocked on localhost** — even after adding 5180 to `ALLOWED_ORIGINS` (it was `http://localhost:5173`, the vite default, NOT the launcher's 5180), the CSRF guard returns **`CSRF_TOKEN_REQUIRED`** (the dev env was never set up to establish a pre-session CSRF cookie on localhost). So **authed flows (login/signup → onboarding, cockpit, admin) CANNOT be reviewed on localhost** — review them on **PROD (`dialer.auxara.io`)**, which has the real cookie/CSRF/origin config. localhost is fine ONLY for unauthed surfaces + static `/explorations/*.html` mocks. *(2026-06-29: the onboarding-page review burned ~25 turns on local-env issues — missing `@csstools/postcss-global-data`, tsx-watch chokidar hang, ALLOWED_ORIGINS port mismatch, CSRF — before Amin said "just merge + test on prod." For an authed FEATURE review, MERGE → test on prod is faster than fighting the localhost auth env.)*
