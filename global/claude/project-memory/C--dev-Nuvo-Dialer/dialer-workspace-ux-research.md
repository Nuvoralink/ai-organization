**Two-wave cited research (2026-06-16) across Convoso/PhoneBurner/Orum/Nooks/Kixie/GoHighLevel/Aloware/Salesloft/Outreach/Close + Dialpad/Aircall/CloudTalk/JustCall/MightyCall/Five9/Talkdesk.** The two waves CONVERGED. (Full sources in the session; fold into `docs/app-plan/product/31-dialer-ux-design-benchmarks.md` with citations at Slice-C closeout — doc-31 anti-staling rule.)

**ADOPT (best-reviewed patterns, cited):**
1. **Single pane of glass** — calls + SMS + context in ONE window, no app/tab toggling (Five9 frames it as killing application-switching + lost context; Dialpad/Aircall/JustCall/Talkdesk "unified view").
2. **Per-lead unified timeline** — calls + VM + SMS + notes in one thread keyed to the contact (Close = "best built-in dialer in any CRM"; JustCall threading = "unique"; Dialpad center thread; MightyCall events history). **← THIS is where SMS lives: same window, threaded to the lead.**
3. **Context pre-loaded at the instant of connect** (Nooks praised; Convoso slow screen-pop hated).
4. **One-key disposition that auto-advances, zero manual steps between calls** (PhoneBurner disposition-macros praised).
5. **Clean/calm, fast-to-learn** (Dialpad/CloudTalk/MightyCall) — explicit counter to the dense tier.
6. **Name + active line always visible mid-call** (MightyCall hidden-line = a named defect).

**AVOID (documented pain, cited):**
1. **Density/clutter overwhelm** — Outreach "a maze," weeks to onboard; Five9 "feels very old"; Genesys "clunky/overwhelming."
2. **Disposition→next-lead friction** — GoHighLevel "click no answer, drag the mouse across the screen to next lead" + forced 15-30s inter-dial delays.
3. **SMS as a separate app/tab** — burying it is treated as a defect (modern tools thread it in).
4. **Cross-surface inconsistency** — Dialpad apps "NO consistency in design" → validates our "same object, same structure" doctrine.
5. **Lag/clunky on the real-time pane; connect-time dead air** (Orum/Nooks robocall-tell; Convoso freezes).

**OUR UNIQUE WORKSPACE IA (synthesis — combines the winners, drops the pain, bounded by ARC-006):** ONE calm lead-centric pane; the call AND the conversation are the same surface.
- **Left rail:** what's next + what needs me — dial queue (up-next, power auto-advance) + inbound replies/VM glance + session stats.
- **Center = THE LEAD** (the LOCKED cockpit): name + active line always visible, Tier-1/2 context (NO CRM clutter — ARC-006), call controls, guided teleprompter (APPROVED 2026-06-16), quick-tags, battlecards = **compact on-demand quick-search** (never covers the lead — the "dump" was the rejected v1).
- **Right = THE LEAD'S UNIFIED TIMELINE:** every prior call + VM + SMS + note in one lead-keyed thread (survives number rotation) + compose-to-text + Book (closer calendar). **SMS's home.**
- **Conversations nav view** = the SAME lead-timeline composite in a full inbox (list · thread · contact) — same object, same structure (the Dialpad-inconsistency lesson).
- **Zero steps between calls:** one-key disposition + auto-advance (no GHL mouse-marathon).
- **Unique-to-us vs a clone:** the single-pane + unified-timeline winners, stripped to a CALM low-density surface bounded by the authority rule (lead shows only name/phone/city-state/local-time + OUR own call/SMS history — no CRM profile/score/deal), power-only, lead-keyed SMS, on-demand battlecards, teleprompter. See [[no-internal-narrative-in-ui]] + [[dialer-not-crm-design-boundary]].

**LOCKED DESIGN DIRECTION (Amin, 2026-06-16, after rejecting the cramped v1-v3 mocks as "cramped, too much info dump, inconsistent, too many buttons"):**
- **Radically minimal LIVE-CALL screen:** show ONLY the lead (name large + active caller-ID/line always visible + timer + ONE demoted context line) + the SCRIPT + exactly TWO primary buttons (Mute, Hang up) + a single "⋯ More" revealing secondary controls (keypad/battlecards/rec/VM-drop) on demand. **NO disposition, NO quick-tags, NO message-glance on the live call.** Generous whitespace. (~3-4 visible buttons, not 15.)
- **Disposition + quick-tags + AI-draft appear ONLY at WRAP-UP** (after hangup) — progressive disclosure by call state.
- **Collapsible ICON nav rail** (~56px icons default, expand to labels on hover) — not a fat rail, not a top dropdown (Amin offered dropdown-or-hideable → chose hideable icon rail).
- **Consistency is a hard requirement:** one button/card/spacing/type scale across cockpit + wrap-up + Conversations (the "inconsistent" rejection). Reuse `_design.css` tokens verbatim.
- Teleprompter design APPROVED; battlecards = compact on-demand search (never a panel dump). SMS = the full Conversations page (history + compose), first-class.

**CORRECTION — STAGE-AWARE, not "minimal everywhere" (Amin, 2026-06-16):** the radically-minimal call screen was ALSO rejected — "way too minimal and full of wasted space." The real answer: the cockpit is **DYNAMIC / stage-aware** — it changes with the call phase, surfacing the right working set per stage and USING the space for it (never dump-everything, never empty). Per-stage working sets:
  - **Idle/between:** built around the QUEUE + next-lead preview + session stats + Start dialing (not an empty call card).
  - **Dialing/ringing:** who you're calling + the OPENING script pre-loaded + Cancel; queue shrinks to a slim "Next: …" strip.
  - **Connected:** the 2-column WORKING cockpit — lead header (always visible) + script (dominant) + quick-tags | Book/Notes (the right column is what fixes the wasted space); Mute+Hang up primary + a compact accessible cluster for keypad/battlecards/rec/VM-drop. NO disposition here.
  - **Wrap-up:** built around the DISPOSITION (one-key chips + AI-draft accept/edit + notes + quick-tags + Save & next); script/controls recede.
  - **"Up next" queue is INTEGRATED + stage-dependent (prominent at idle, slim strip on a call) — NOT a standalone floating card.**
  - **Nav-crash fix:** the collapsible rail must NOT toggle `position` on `:hover` (relative→absolute removes it from flow → cursor-loss → infinite hover/reflow loop = page crash). Keep it always-absolute in a fixed 56px column; animate WIDTH only on hover.
  - **Calibration test:** any large empty region = wrong stage layout (give it stage-appropriate content); any wall-of-always-visible-buttons = too much. Middle ground per stage.

**SMS IS A CROSS-CUTTING CAPABILITY, NOT JUST A PAGE (adversarial SMS pressure-test 2026-06-16, Amin: "you missed it everywhere"):** the Conversations PAGE (3-pane, lead-keyed, templates) is good; the failure was REACHABILITY — SMS was unreachable from 4 of 7 booker states, no persistent affordance, no in-call action, the no-answer "Send SMS" the banner CLAIMED didn't exist in markup, and the wrap-up CONV-004 combo SMS limb was absent. The fix (being mocked → re-approval; build into Slice C): **(1) a persistent shell-level communicator DOCK** (bottom-right pill + unread badge from the SAME count as the rail Conversations dot; expands to Dialpad + Messages tabs; a LAUNCHER into the same lead-keyed thread, never a 2nd store). **(2) connected control-strip "Text" action** (peer to VM-drop, hotkey T → compact composer popover, morph-in-place not screen-swap, prefilled to the on-call lead's thread, template-first + compose fallback, shows the From number). **(3) no-answer "Text" one-tap** (sibling to Leave VM; pre-loads a follow-up template the human sends). **(4) wrap-up disposition-combo SMS limb** (UX-DO-009 save+optional-SMS+advance; disposition-tied template, opt-in). **(5) every SMS affordance renders an honest 10DLC-not-vetted DISABLED state** ("SMS needs 10DLC — finish setup" → 10DLC dashboard; US-scoped, Canada works immediately). **Authority (ARC-006 + CONV-004 ladder):** all SMS human-triggered = Tier-2 OK; CONV-004 is a 3-level Send-Authority Ladder — L0 manual / **L1 auto-LOAD-draft + human-send = DEFAULT** / L2 bounded auto-send (opt-in, default-OFF + global kill switch) — so no-answer/wrap-up SMS = pre-load draft the human confirms, NEVER auto-send by default. Compliance gates (calling-hours, STOP/consent) run on EVERY send deterministically. **Doc-fix for closeout:** doc-31 §5b power-cockpit checklist has NO SMS line — structural gap; add an SMS-touchpoint row. The dock + in-call SMS are NEW surfaces → mockup-first + Amin sign-off + doc-31 §5 checklist + ARC-006 before coding.

**COMMUNICATOR DOCK — corrected design (adversarial REJECT + cited research, 2026-06-16):** the first dock build was rejected (Amin + adversarial): a single "Messages 3" pill that expanded to BOTH Dialpad+Messages tabs (misleading mislabel); the dialpad reinvented the LOCKED `manual-dial.html` dialpad with stripped tokens (`--surface-2`/`--hairline` not `--surface-solid`/`--edge`, no hover/press cycle) + a bespoke green Call button with a raw `oklch()` literal instead of the iris `btn glow` (= "basic black/white" look); the translucent panel floated glass-over-glass on the translucent cockpit with no elevation step (looked weird); and it carried a manual dialpad that bypassed the CMP-012 calling-hours gate. **Settled resolution:** **TWO separate icon launchers** in the bottom-right dock (Messages = speech-bubble icon + unread badge, NO text label; Dial = keypad icon) — NOT one tabbed pill. **The quick-Dial STAYS** (Amin's instinct, cited-research-confirmed: every power dialer — Kixie/PhoneBurner/JustCall/Aircall/Dialpad — ships a keypad one tap away in the persistent dock; agents use it several times/shift for callbacks/double-tap-redial/prospect-gives-a-number/wrong-number-redial; absence is the loud complaint, e.g. GHL "it kills my session"). **HOW (decisive):** (1) **EMBEDDED compact popover, NOT a launcher to the full manual-dial page** — sending an agent to a full page for one dial is the documented anti-pattern (GHL session-break). (2) The Dial popover **REUSES the locked manual-dial dialpad component** (`.key` recipe + "calling from" smart caller-ID line + calling-hours guard + `btn glow`), so **compliance rides on the DIAL not the list** — calling-hours/DNC gate comes along for free, one code path, no second keypad that can drift/skip the gate (research: manual dial differs from auto only on the ATDS/autodialer axis — which doesn't apply to our agent-initiated single-line engine anyway; DNC + calling-hours apply regardless of how a call is initiated). (3) Keep the Dial popover to keypad+search+calling-from+Call ONLY (ARC-006 — no queue-mgmt/callback-scheduling/lead-lookup). Both popovers: opaque `--surface-solid` + distinct overlay elevation + anchored to grow UPWARD from the launcher (no glass-over-glass). Messages popover reuses the SAME Conversations thread-row composite (not a hand-rolled `.dock-tl`). Dock is a NEW surface → locked-surfaces.md entry after sign-off; the dialpad inside is the locked component unchanged. **DESIGN-DRIFT LESSON (doctrine-loop Arm 1):** a new exploration reused a *different* treatment than the locked surface for the same component (dialpad, thread row, Call button) — no gate caught it. Process fix: any new exploration touching an already-locked component must diff its tokens against the locked source before review (design-baseline verification applied to explorations, not just React).

**SURFACE-MATERIAL CONSISTENCY RULE (Amin flagged "inconsistent — one full black then glass-frost; light mode just white", 2026-06-16) — the locked `_design.css` system's own intent, now the enforced rule:** the system is "calm-led with cockpit atmosphere"; `--glow` = "the ONE live action only"; `--glass` = the cockpit. **Root cause of the drift:** the mock OVERRODE the app interior — `.main { background: var(--canvas) }` (a solid near-black dark / near-white light) — so the `--ambient` colored atmosphere only survived at the shell edges → "full black" in dark, "just white" in light; AND card materials were mixed at random (idle/dialing/connected/wrap used `--glass` while the session panel/queue-empty/conversations used flat `--surface`). **The consistent rule (apply on EVERY surface, BOTH themes) — CARDS ARE GLASSY, NEVER FLAT (Amin corrected me twice: "the cards being solid basic black cards, didnt we decide the cards be a bit glassy?" + "i dont want it flat black or flat white… update the light mode too"):** (1) the app **interior carries `--ambient`** (never a flat `--canvas` fill), both themes; (2) **NO card is the flat `--surface`/`--surface-solid` fill** (that reads solid-black in dark / solid-white in light — the bug). Two GLASS tiers: between-calls cards (idle `.nextlead`, "This session" `.card`, queue-empty, `.noanswer-card`, `.conv`) = the calmer **`--glass-soft`** (a new token: subtle iris-tinted frosted base `oklch(0.295 0.025 268/0.62)` dark / `oklch(0.985 0.014 274/0.62)` light + `--glass-edge` + `blur(16) saturate(1.1)` + `--glass-top`); in-call cockpit (dialing→connected→wrap) = the **richer `--glass`** (`blur(24) saturate(1.2)`); inner type-into elements (script/notes/keypad/inputs) stay `--surface-2`+`--recessed`; small controls/chips/icons stay `--surface-solid`; (3) **glow ONLY on the live connected `.cc.live` + the one `btn glow`** (the cockpit stands out via glow, not by being the only glassy thing); (4) "play with glassyness/frost per stage/category" is allowed — vary intensity, NEVER flat. Verify BOTH light + dark. **LESSON: I guessed the consistency direction WRONG (chose calm flat `--surface` cards) when Amin wanted GLASSY everywhere — should have confirmed the direction on a taste fork instead of guessing; cost 2 extra passes.** **DOCTRINE-LOOP Arm 1 (gate the class):** explorations live outside the `check:ui-*` gate tree, so the flat-`--canvas`-interior + mixed-material drift wasn't caught — a future gate should flag a stage container that paints a flat solid (`--canvas`/raw bg) instead of `--ambient`, and a non-cockpit card using `--glass`. Same lesson as the dock: explorations must diff their treatment against the locked surfaces before review.

**SCROLL-ON-CARD DESIGN DECISION (Amin, 2026-06-18 — "make that a design decision, everything scrollable needs to be designed like this on cards"):** every scrollable region that sits on a card uses ONE treatment (codified as a reusable `.scroll-soft` class in the mock; in the real build → a `ScrollArea` design-system primitive): (1) content scrolls DIRECTLY on the card — NO inner card-in-card (transparent bg, no border/box-shadow/radius on the scroller OR its inner content wrapper); (2) an OPACITY FADE (CSS mask linear-gradient, ~16-18px) at the top + bottom scroll boundaries so content fades in/out, never hard-clips; (3) scrollbar HIDDEN (overlay scroll: `scrollbar-width:none` + `::-webkit-scrollbar{width:0}`); (4) any pinned nav (the script's "Jump to" section row) lives OUTSIDE the masked scroll (crisp, always accessible) wired to scroll the real container. Applies to: the cockpit script (`.cc-script` — the reference), the dialing-stage script preview, the connected right-column recent-activity list, the Conversations thread, the dock messages list — ALL of them. Connected-stage reference impl: `.cc-script` mask + the `jump-pinned` JS (moves `.jump` out of `.cc-script` to `.cc`, wires chips to scroll `.cc-script` to `#sec-*`). The earlier "recessed bordered box" treatment for the script was REJECTED as a card-in-card — transparent + fade is the answer.
