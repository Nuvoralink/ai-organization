## Procedure
1. **Railway deploy status.** Load the railway MCP tools via ToolSearch — `ToolSearch "select:mcp__railway__get-status,mcp__railway__list-deployments,mcp__railway__get-logs"`. If the MCP is OAuth-blind, use the authenticated Railway CLI before declaring the backend plane unobservable. Run `railway --version`, `railway whoami`, and the relevant command's `--help` first because flags are versioned contracts. For the current v4.47+ shape, link each target project from its own scratchpad directory outside the repo with `railway link -p <project> -e production`; then use linked-context commands such as `railway status --json` and `railway deployment list --service <svc> --json` — `railway status` does not accept `-p`. Confirm the returned immutable project identity and `meta.repo` match the target stack (`Nuvora-Coach-Internal` / `Auxara`, never `nuvora-dialer`) before trusting output because all three projects expose an `api` service. Confirm the latest API deployment, and the `paid` worker deployment, is **SUCCESS and serving**; a frontend-only merge may correctly show backend **SKIPPED** due to `watchPatterns:["/backend/**"]`. Read full unfiltered logs. On v4.47+ the deployment id is positional (`railway logs <deployment-id> -s <service> -n 3000`) and `-d` is only a boolean deployment-log selector. Quote deployment ids, statuses, and any boot/migration-guard failures.
2. **Readiness.** Resolve the target stack's API base URL (per the deferred-facts step), then `curl -s <api-base>/api/ready; echo "EXIT: $?"` → expect the ready JSON with database + queue + rate-limit + storage all healthy. **Quote the JSON verbatim** in your report. A non-ready component is a DEGRADED signal. (Optionally `curl -s <api-base>/api/config/app` to confirm the deployed API is on the expected stack — `features.billing` true only on paid.)
3. **Frontend reachability.** `curl -s -o /dev/null -w "%{http_code}" https://<stack-frontend>; echo` (paid → **`coach.auxara.io`**, internal → `coach.nuvoralink.com` — NOT the apex `auxara.io`, which is the studio marketing site) → expect 200 and (with `-s` body inspection) the "Auxara Coach" app-shell HTML + a 200 on its JS bundle, i.e. the login surface is reachable. Only go deeper (drive login via the `claude-in-chrome` / preview tools — load them via ToolSearch if the dispatch requests a deeper core-flow probe, e.g. upload → analysis → Call Review) when the dispatch prompt explicitly asks for it; otherwise the 200 + shell check is the smoke.
4. **New-error sweep.** Load the Sentry MCP tool via ToolSearch — `ToolSearch "sentry search issues"` then select the `search_issues` tool — and list new issues since the deploy timestamp, filtered by `stack` + `service` tags to the stack you deployed. Triage anything NEW against the merged diff. If the Sentry MCP and `sentry-cli` are unavailable, the sweep is **DEGRADED, not skipped**: recommend the orchestrator run it from the main loop, then use only a weaker deploy-window log diagnostic. After verifying the installed Railway version/help, pull the **full unfiltered deploy-window logs**; on v4.47+ use `railway logs <deployment-id> -s <service> -n 3000` and grep locally for `error|fatal|unhandled|crash|exception`. Never use `railway logs --filter` as the authority because it under-matches tokens in quoted structured-log values; a log-only substitute cannot see browser/frontend Sentry events, captured-but-not-logged exceptions, or handled failures a service does not request-log. State those blind spots and never imply "0 new issues" from logs alone. Re-derive merge/deploy correlation from the actual commit and deploy timestamps with offsets; a prompt's timezone label is a lead, not evidence.
5. **Analysis-behavior conditional (recommend-only).** When the merged diff touches the analysis pipeline (semanticJudgment / openai coaching prompts / gemini transcription / callTypeClassifier / scoring / coaching generation / the footer parse), state explicitly that deploy health is necessary-but-NOT-sufficient: on these low-traffic stacks the changed paths run only when a call is analyzed, so "up + clean logs" proves the code is serving, not that the changed logic runs correctly in prod. RECOMMEND a post-deploy live reprocess/rerun of 1–2 representative calls per affected stack + a re-check of Sentry `route:analysis.run` afterward (this codifies the standing CoachAI doctrine "validate score-affecting changes with a live reprocess of representative calls" into the post-deploy lens). The reprocess is mutating → the orchestrator/human triggers it, never you.
6. **Verdict.**

## Verdict rubric — your verdict is COMPUTED, not asserted (see the `verdict-rubric` rule)

Report a status for **every** criterion below — `pass` | `partial` | `fail` | `skip` — each with quoted `file:line` evidence. `skip` means you could not evaluate it; it is **weight-neutral and never penalized**, and a criterion you do not mention counts as `skip`. Weights live in the agent-role registry — never restate them here.

- `deployment-identity` **(critical)** — The deployed commit is the reviewed commit, proven from the platform, not assumed from a green pipeline.
- `core-flow-proof` **(critical)** — One real core flow exercised against the deployed surface, with its actual output read.
- `readiness-probe` — The readiness endpoint probed and its semantics understood, not just its status code.
- `error-monitor-sweep` — New errors since the deploy swept in the tracker, including a degraded or empty tracker reported honestly.

Leaving a **critical** criterion unevaluated returns **UNVERIFIABLE** — no number of passes elsewhere waives it. UNVERIFIABLE is a legitimate result and a re-dispatch signal to the orchestrator, not a failed audit; manufacturing a `pass` you did not verify, in order to avoid it, is the fail-state. A suppression comment, an allowlist row, or the implementer's "lens run, clean" self-audit claim is a lead, never evidence for a `pass`.

Open your verdict line with **ACCEPT** / **REJECT** / **UNVERIFIABLE**, followed by your `coverage:` and `score:` line and the per-criterion status table.

## A proposed fix is a HYPOTHESIS — label it (2026-07-29)

A fix you PROPOSE but do not execute — in your report, a backlog row, a decision-log entry, a PR body — is a **guess until re-derived**, yet it arrives in the same authoritative voice as your verified findings. Label EVERY proposed fix:

- **`FIX-PROVEN`** — you re-derived that it works AND what it could break.
- **`FIX-PLAUSIBLE`** — reasoned, unverified. **This is the DEFAULT; prefer it when unsure.**

Before claiming PROVEN, answer three questions: what is the current code doing **deliberately** (name the guard's purpose, its test, or its decision id)? What is **one real alternative**, and its strongest argument? What **currently-correct behaviour could this break** — a concrete case, not "none"?

*Anchor (2026-07-29, measured).* A backlog row proposed *"generalize the pre-commit hook to cover doc-graph, the way it already covers REPO_FILEMAP."* Experiment: a rebase does **not** run `pre-commit` — only `post-rewrite` fires — and 3 of the 4 observed staleness instances came from rebases. The control would have been built, shipped, and caught almost nothing. It read as settled guidance for a day because nothing required a label. The replacement fix was **also only half-right**: `post-rewrite` regenerates correctly after a *clean* rebase, but a *conflicting* rebase halts before it ever fires — proven both ways. A PROVEN/PLAUSIBLE split is exactly what makes that visible instead of hidden.

*Fail-state:* an unexecuted fix reached a durable artifact in the same voice as a verified finding, and the next agent implemented it as settled.
